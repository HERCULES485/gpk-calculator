# CLAUDE.md

Процессуальный калькулятор сроков: считает сроки по кодексам процессуального
права на основе дат, норм и производственного календаря.

## Границы модулей — соблюдать строго

- `src/` — домен ГПК (Гражданский процессуальный кодекс). Логика, данные и
  тексты норм для сроков ГПК.
- `apk/` — домен АПК (Арбитражный процессуальный кодекс). Появится по мере
  разработки параллельного модуля — вся работа по задачам АПК ведётся
  только здесь.
- `core/` — общий предметно-независимый движок (расчёт дат, версионирование
  норм, механика перерыва срока, экспорт), используется как библиотека
  обоими доменами. НЕ содержит предметных данных ни одного кодекса.
- `web/` — пользовательский интерфейс ГПК-калькулятора. Не связан с
  АПК-модулем.

Правило: задача, сформулированная в контексте одного домена (ГПК или АПК),
не должна затрагивать файлы другого домена или core/, если это явно не
указано в самой задаче. Если в процессе работы кажется, что правка в
"соседнем" домене или в core/ была бы уместна или упростила бы задачу —
остановись и спроси, а не делай это по собственной инициативе.

## Проверка

- `npm test`
- `node scripts/smoke.mjs`
- `node scripts/smoke-apk.mjs`
- `node scripts/smoke-bankruptcy.mjs`

Все четыре гоняются в GitHub Actions на каждый push и pull_request.
При мерже в main GitHub Pages передеплоивается автоматически.

Подробная архитектура — в `SPEC.md` и `docs/core-extraction-audit.md`, не
дублировать их содержимое здесь.

## Мерж в main

Мерж пул-реквестов в main выполняет только архитектор лично, вручную, через
интерфейс GitHub. Это правило без исключений — оно действует даже для
механических правок по уже подтверждённому образцу, даже когда явного
запрета на мерж нет в конкретном промпте задачи. Claude Code открывает PR,
дожидается зелёных чеков именно на PR (событие pull_request, не push) и
докладывает об этом — саму кнопку merge не нажимает никогда.

## core/ — правки только по разрешению

`core/` — общий движок обоих доменов. Правки в `core/` вносятся
только по явному разрешению архитектора, точечно и аддитивно (без
рефакторинга), с обязательным полным прогоном тестов на регресс.
Если во время работы над задачей одного домена кажется, что решением
было бы поправить `core/` — остановиться и спросить, не делать по
своей инициативе.

## Узлы и тесты

Новые узлы и тесты добавляются строго в конец соответствующего
файла, без реорганизации уже существующих. Сборка результата узла —
только через `computeSimpleTerm`/`computeInterruptibleTerm`/
`computeDeadline` из `core/`, никогда вручную.

## kind карточки

Фиксированный набор: `term`, `event`, `window`, `capped_term`,
`not_applicable`, `error`. Новый `kind` не вводится по собственной
инициативе — это архитектурное решение, не деталь вёрстки.

Restoration-узел создаётся только если в самой норме есть числовой
предельный срок восстановления. Если такого потолка в норме нет —
restoration-узел не создаётся вообще.

## apk/ — банкротство отдельно от процессуальной цепочки

Внутри `apk/`: `apk/chain.js`/`apk/views.js`/`apk/situations.js`/
`apk/labels.js` — процессуальная цепочка АПК. `apk/bankruptcy*.js` —
отдельный закон (ФЗ № 127-ФЗ), не часть цепочки АПК, узлы не делят
между собой ни якорей, ни полей ввода. Файлы этих двух групп не
смешивать.

## Первые-в-своём-роде задачи

Для задачи, где используется механика, узел или файл, которого
раньше не было в живом рендере/на странице (не только в тестах) —
не коммитить и не открывать PR сразу, сначала показать diff (и
скриншоты/сырой outerHTML, если речь о новой вёрстке) на проверку
архитектору. Перенос по уже использованному образцу — коммитить и
открывать PR можно сразу по завершении.

## Модель

Если модель, под которой реально запущена сессия, не совпадает с
той, что указана в задаче — сообщить об этом явно в докладе, не
продолжать молча на другой модели.
