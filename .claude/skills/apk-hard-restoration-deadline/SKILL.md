# Узел восстановления процессуального срока с дифференциацией по субъекту

## Когда применяется этот паттерн

Часть статьи АПК РФ имеет структуру: «срок... пропущенный по причинам, не
зависящим от лица... может быть восстановлен... при условии, что ходатайство
подано не позднее чем через N месяцев со дня X, или, если ходатайство подано
лицом, указанным в статье 42 настоящего Кодекса, со дня, когда это лицо
узнало или должно было узнать о нарушении его прав...».

Это НЕ то же самое, что вопрос «будет ли суд считать причины пропуска
уважительными» — та часть нормы (обычно отдельное предложение или отдельный
пункт Постановления Пленума) не вычисляется, это судебное усмотрение. Узел
считает только формальный крайний срок подачи ходатайства.

## Три категории субъекта (форма, не цифры)

1. Участвовавшее в деле лицо, надлежаще извещённое о разбирательстве. Якорь —
   точка отсчёта, названная в первой части нормы буквально (для ст. 259 это
   дата решения; для ст. 276 — дата вступления в силу; для каждой новой
   статьи это нужно установить заново по её тексту, не предполагать по
   аналогии).
2. Лицо, указанное в ст. 42 АПК РФ — не участвовавшее в деле, чьи права или
   обязанности затронуты актом. Якорь — дата, когда лицо узнало или должно
   было узнать о нарушении своих прав. Названа буквально в тексте самой
   части 2.
3. Участвовавшее в деле лицо, ненадлежаще извещённое о времени и месте
   заседания. Та же точка отсчёта, что у категории 2, но другое правовое
   основание. Эта категория обычно не названа в тексте самой статьи АПК —
   она появляется в разъяснении Пленума (для ст. 259 — п. 14 Постановления
   № 12; для ст. 276 — п. 10 Постановления № 13). Для новой статьи
   необходимо отдельно искать, есть ли для неё аналогичное разъяснение — не
   переносить автоматически с других статей и не считать её универсальной
   чертой любого восстановления.

Не считать заранее, что категорий ровно три. Это подтверждено дважды на
похожих по конструкции статьях одного кодекса — не факт, что так будет для
любой нормы с похожей первой фразой. Всегда сверять фактический текст статьи
и относящегося Постановления Пленума.

## Форма кода (по образцу apk/chain.js)

```js
const <NAME>_SUBJECT_CATEGORIES = new Set([
  'participating_duly_notified',
  'article_42_person',
  'participating_improperly_notified',
]);

export function compute<Name>Restoration(inputs) {
  const category = inputs?.subject_category;
  if (!<NAME>_SUBJECT_CATEGORIES.has(category)) {
    throw new Error(
      `subject_category должен быть одним из: ${[...<NAME>_SUBJECT_CATEGORIES].join(', ')}`,
    );
  }

  let anchorInput;
  if (category === 'participating_duly_notified') {
    // Якорь этой категории — по тексту конкретной статьи. Если он сам
    // вычисляется другим узлом (как у cassation через entry_into_force_apk),
    // вызывать тот узел напрямую и брать его результат — не дублировать
    // его логику здесь.
  } else {
    anchorInput = inputs.learned_of_violation_date;
    if (anchorInput == null) {
      throw new Error(`Для категории ${category} обязательна learned_of_violation_date`);
    }
  }

  const calc = computeSimpleTerm(<TERM_OBJECT>, anchorInput);
  return { ...calc, subject_category: category };
}
```

Имя входного поля для категорий 2 и 3 стабильно: `learned_of_violation_date`
— переиспользовать буквально это имя, не изобретать новое для каждой статьи.

## Что НЕ включать в term-объект узла (декоративные поля)

- `restoration_norm` — узел сам и есть вычисление восстановления, текстовая
  подсказка-ссылка на себя бессмысленна.
- `ics` — пока ни один реестр apk/ не сканирует экспорты модуля, поле будет
  нерабочим. Добавить в задаче UI/ics-связки, когда она случится.
- `anchor.event` — не читается движком (подтверждено аудитом core/engine),
  добавляет вводящее в заблуждение впечатление о контракте узла.

## Обязательный набор тестов

1. Категория 1: обычный случай, сверить, что якорь — правильная точка
   отсчёта данной статьи (не соседняя дата по ошибке).
2. Категория 2 (ст. 42): обычный случай от learned_of_violation_date.
3. Категория 3 (если подтверждена для этой статьи): своя дата, отличная от
   дат в тестах 1–2 — явно показать, что категория не спутана с другими.
4. Перенос через нерабочий день — дату получать прогоном настоящего
   computeDeadline, не выдумывать.
5. Правило «нет такого числа» для длительности этой статьи.
6. subject_category отсутствует/неизвестна — ошибка со списком допустимых
   значений.
7. Каждая категория без своего обязательного поля — отдельная ошибка,
   называющая недостающее поле.
8. Если якорь категории 1 делегирован другому узлу (как cassation →
   entry_into_force) — отдельный тест, что ошибка валидации того узла
   всплывает наружу, а не проглатывается.
9. Результат несёт subject_category, совпадающий с переданным.
10. restoration_norm и ics на term-объекте — undefined.

## Перед использованием этого skill на новой статье

1. Сверить точный текст части статьи и относящихся пунктов Постановления
   Пленума по Project Knowledge — не по памяти о том, как было в ст. 259
   или 276.
2. Установить: сколько категорий у ЭТОЙ статьи (2 или 3), сколько месяцев,
   какая точка отсчёта у категории 1.
3. Если что-то расходится с этим skill'ом — расхождение важнее сходства:
   фиксировать его явно в промпте, не подгонять под уже готовый шаблон.
