# Шаг 12: инвентаризация словарей подписей перед объединением

**Статус:** результат Части 0 задачи «объединить дублирующиеся словари
подписей ГПК» (`docs/core-extraction-audit.md`, §3 примечание 3 и §4,
строка 12). Изначально документ только фиксировал факты, не меняя код; после
того как решение по трём спорным формулировкам было принято отдельно (см.
§5), словарь `INPUT_LABELS` объединён в `src/labels.js` — см. §5 и
обновлённый §4.
**Повод:** прежде чем переносить что-либо в `src/labels.js`, для каждого из
пяти словарей, названных в аудите (§1.2, фрагмент 11), нужно установить,
существует ли он в обоих файлах и идентичны ли значения.

## 1. `INPUT_LABELS` — единственный подтверждённый дубликат, с расхождениями

Определён в `src/views.js:63–131` (52 записи) и `web/app.js:31–109`
(57 записей). Сверка ключ-в-ключ:

### 1.1. Ключи, которых нет в `src/views.js` (есть только в `web/app.js`)

| Ключ | `web/app.js` | Строка |
|---|---|---|
| `simplified_appeal_ruling_reasoned_date` | «Дата изготовления мотивированного апелляционного определения (упрощённое производство)» | 49–50 |
| `default_judgment_appeal_ruling_reasoned_date` | «Дата изготовления мотивированного апелляционного определения (заочное решение)» | 57–58 |
| `mirovoy_appeal_ruling_date` | «Дата принятия апелляционного определения районного суда» | 68 |
| `periodic_payment_indefinite` | «Срок, на который присуждены платежи, не определён (бессрочное взыскание)» | 72 |
| `foreign_state_default_judgment_appeal_ruling_reasoned_date` | «Дата изготовления мотивированного апелляционного определения (заочное решение против иностранного государства)» | 94–95 |

Обратного расхождения нет: все 52 ключа `src/views.js` присутствуют в
`web/app.js`.

### 1.2. Общие ключи с разным текстом

| Ключ | `src/views.js` | `web/app.js` |
|---|---|---|
| `default_judgment_cancellation_date` | `views.js:84` — «Дата определения об отмене заочного решения (заявление удовлетворено)» | `app.js:54` — «Дата определения об отмене заочного решения» |
| `review_ground` | `views.js:121` — «Основание пересмотра (глава 42 ГПК)» | `app.js:97` — «Основание пересмотра» |
| `review_circumstance_date` | `views.js:122` — «Дата обстоятельства (зависит от основания)» | `app.js:100` — «Дата обстоятельства (выберите основание выше)» |

Контекст, установленный чтением кода (не влияет на решение, но полезен для
проверки):

* `review_ground` в `web/app.js` рендерится напрямую как подпись
  `<select>` (`renderChoiceField('review_ground', …)` → `INPUT_LABELS[id]`,
  `web/app.js:1479`) — то есть пользователь реально видит «Основание
  пересмотра» без ссылки на главу 42, в отличие от текста в `views.js`.
* `review_circumstance_date` в `web/app.js` — фолбэк-заглушка: комментарий
  на `web/app.js:98–99` прямо говорит, что при выбранном основании подпись
  берётся из `ground.date_label` (`REVIEW_GROUNDS`, `renderReviewGroundFields`,
  `web/app.js:1774–1798`), а значение из `INPUT_LABELS` показывается только
  когда основание ещё не выбрано.
* `default_judgment_cancellation_date` использован в `views.js` через
  `genericMissingInputs(ids, inputs, INPUT_LABELS)` (`views.js:173`) —
  прямое отображение без переопределения.

Это не опечатки форматирования — разный юридически значимый текст подсказки
для одного и того же поля в трёх случаях, плюс пять полей, подписанных
только в одном из двух мест. Согласовывать эти расхождения самостоятельно
не стал: по условиям задачи выбор верной версии требует решения человека и
не принимается автоматически. Решение по всем трём было запрошено отдельно
(вопросами с рекомендацией и обоснованием по каждому пункту) и получено —
см. §5, где оно применено и `INPUT_LABELS` объединён в `src/labels.js`.

## 2. `INPUT_HINTS`, `FOLLOW_UP_FIELDS`, `REDACTION_FIELD`, `GENERAL_CHAIN_NODES` — не дублированы

Аудит (`docs/core-extraction-audit.md`, фрагмент 11) перечисляет эти четыре
имени рядом с `INPUT_LABELS` в описании `web/app.js`, но не называет их
«вторым экземпляром» — этот термин там применён только к `INPUT_LABELS`
(фрагмент 10). Проверка (`grep` по `src/`, `web/`, `core/`) подтверждает:
все четыре определены **только в `web/app.js`** и в `src/views.js`
(и вообще нигде в `src/`) отсутствуют полностью — ни под тем же именем, ни
под похожим:

* `INPUT_HINTS` — `web/app.js:110` (плюс отдельный `INPUT_HINTS_EXPIRED` на
  `web/app.js:225`, тоже без пары в `views.js`).
* `FOLLOW_UP_FIELDS` — `web/app.js:1313`.
* `REDACTION_FIELD` — `web/app.js:1521`.
* `GENERAL_CHAIN_NODES` — `web/app.js:242`.

Это объяснимо архитектурно: `src/views.js` собирает предметные данные
карточек (модель), а перечисленные четыре словаря управляют **рендерингом
в DOM** — подсказки под полем, набор доследующих вопросов, редактирование
полей, список узлов общего порядка для UI без выбранной ситуации. Это
исключительно обязанность `web/app.js`, второго потребителя для них никогда
не было.

Так как объекта дублирования нет (пункт (a) — «нет» для всех четырёх),
пункт (b) неприменим, а пункт (c) («разные сущности с одинаковым именем»)
тоже не подходит буквально — имя не переиспользовано, оно просто не
существует во втором файле. В любом случае итог один: переносить нечего,
эти четыре словаря вне рамок этой задачи. Оставлены без изменений.

## 3. Проверено дополнительно — используются ли в `views.js` 5 ключей, отсутствующих в его `INPUT_LABELS`

Открытый вопрос: 5 ключей из §1.1 (`simplified_appeal_ruling_reasoned_date`,
`default_judgment_appeal_ruling_reasoned_date`, `mirovoy_appeal_ruling_date`,
`periodic_payment_indefinite`, `foreign_state_default_judgment_appeal_ruling_reasoned_date`)
существуют только в `INPUT_LABELS` из `web/app.js`. Раз в `src/views.js`
записей с такими ключами в самом словаре нет, вопрос — обращается ли
`views.js` к своему (неполному) `INPUT_LABELS` по одному из этих 5 id через
`missingInputs(ids, inputs)` (локальная обёртка над
`genericMissingInputs(ids, inputs, INPUT_LABELS)`, `views.js:172–174`). Если
да — `genericMissingInputs` получит `undefined` вместо текста подписи, и
пользователь увидит пустое/некорректное место в списке «что ещё уточнить».

**Способ проверки:** найдены все вызовы `missingInputs(...)` в
`src/views.js` (`grep -n "missingInputs\s*("`) — их 9
(`views.js:456, 545, 757, 780, 804, 830, 943, 1061`, плюс определение на
`172`). Часть вызовов передаёт литеральный массив id, часть — переменную;
для каждой переменной источник прослежен до места формирования массива:

* `views.js:757, 780, 804, 1061` — литералы `['appeal_ruling_date']`,
  `['appeal_ruling_reasoned_date']`, `['appeal_filed_date']`,
  `['reasoned_decision_date']`. Ни один из 5 искомых id.
* `views.js:830` — переменная `missing`, присваивается на `views.js:820–823`
  одним из двух литералов: `['ksoyu_ruling_reasoned_date']` или
  `['ksoyu_ruling_date']`. Ни один из 5 искомых id.
* `views.js:456, 545` — переменная `dj.appeal_blocked.missing`. `appeal_blocked`
  формируется в `src/chain.js:1975` (обычное заочное решение) и
  `src/chain.js:2307` (заочное решение против иностранного государства) —
  единственные присвоения `missing:` в обоих объектах: `['default_judgment_refusal_date']`
  и `['foreign_state_default_judgment_refusal_date']` соответственно. Ни один
  из 5 искомых id (в частности, не `default_judgment_appeal_ruling_reasoned_date`
  и не `foreign_state_default_judgment_appeal_ruling_reasoned_date`, несмотря
  на похожие имена).
* `views.js:943` — переменная `terms.review_new_circumstances_missing`,
  которая приходит из `reviewResult.missing`
  (`src/chain.js:897`, `reviewResult = computeReviewNewCircumstancesResult(inputs ?? {})`).
  Функция `computeReviewNewCircumstancesResult` (`src/chain.js:1421–1429`)
  возвращает `missing: null` для всех оснований, кроме
  `vs_practice_change_ground_id`, для которого вызывается
  `computeVsPracticeChangeTerm` (`src/chain.js:1319` и далее) — там
  `missing` строится только из `review_refusal_ruling_received_date`,
  `review_publication_date` и `review_last_act_entry_into_force_date`
  (`src/chain.js:1325–1333`). Ни один из 5 искомых id.

**Вывод:** ни один из 5 идентификаторов не встречается ни в одном вызове
`missingInputs()` в `src/views.js` — ни как литерал, ни через переменные
(их источники в `src/chain.js` тоже не производят эти 5 id). Значит,
`genericMissingInputs` не получает `undefined` для этих полей в текущем
коде, и пользователь не видит пустого/некорректного места из-за этого
расхождения. Расхождение из §1.1 (5 ключей отсутствуют в `INPUT_LABELS`
`views.js`) остаётся зафиксированным как факт для будущего решения по
объединению словарей, но само по себе оно сейчас не проявляется как
видимый пользователю дефект. Код не менялся.

## 5. Решение по трём расхождениям и объединение `INPUT_LABELS`

Решение запрошено отдельно по каждому из трёх пунктов §1.2, с рекомендацией
и обоснованием для каждого — выбрана формулировка `src/views.js` во всех
трёх случаях:

| Ключ | Принятый текст | Обоснование |
|---|---|---|
| `default_judgment_cancellation_date` | «Дата определения об отмене заочного решения (заявление удовлетворено)» | Поле участвует в расчёте (`chain.js`) только в ветке, где заявление об отмене удовлетворено — иначе используется отдельное поле `default_judgment_refusal_date`; уточнение точно описывает условие. Парное поле для иностранного государства (`foreign_state_default_judgment_cancellation_date`) уже содержит то же уточнение в обоих файлах — выбор согласуется с уже существующим прецедентом. |
| `review_ground` | «Основание пересмотра (глава 42 ГПК)» | Ссылка фактически верна (глава 42 ГПК РФ — «Пересмотр по вновь открывшимся или новым обстоятельствам»); словарь `web/app.js` сам использует тот же паттерн для других полей (например, «…(глава 22.2 ГПК)» у `child_return_*`, `web/app.js:74,76`), так что отсутствие ссылки здесь — вероятный недосмотр, а не осознанное решение. |
| `review_circumstance_date` | «Дата обстоятельства (зависит от основания)» | Нейтральная формулировка подходит и для карточки «что уточнить», и как фолбэк на форме. Текст `web/app.js` («…выберите основание выше») был верен только в контексте конкретной раскладки формы (комментарий на прежнем `web/app.js:98–99` прямо это оговаривал) и не годился бы, например, для списка «что уточнить». |

С учётом решения `INPUT_LABELS` объединён в новый файл `src/labels.js`:
единый словарь (57 записей — все ключи из обоих прежних словарей, включая 5
ключей из §1.1) с тремя спорными значениями, зафиксированными как в таблице
выше. `src/views.js` и `web/app.js` больше не определяют собственных копий
`INPUT_LABELS` — оба импортируют его из `src/labels.js`.

Что это меняет для пользователя:
* Список «что ещё уточнить» (`src/views.js`) и форма (`web/app.js`) теперь
  показывают один и тот же текст для всех трёх ранее расходившихся полей.
* Для `review_ground` подпись на форме (`renderChoiceField`) отныне включает
  «(глава 42 ГПК)» — раньше не включала.
* Для `default_judgment_cancellation_date` подпись на форме отныне включает
  «(заявление удовлетворено)» — раньше не включала.
* Для `review_circumstance_date` фолбэк на форме (когда основание ещё не
  выбрано) теперь показывает «(зависит от основания)» вместо «(выберите
  основание выше)»; поведение (подстановка `ground.date_label` после выбора
  основания, `web/app.js`, `renderReviewGroundFields`) не изменилось.
* 5 полей из §1.1, ранее подписанных только на форме, теперь имеют
  подпись и для списка «что уточнить» — на практике не проявлялось (см. §3),
  но словарь стал полным на будущее.
